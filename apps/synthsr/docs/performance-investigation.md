# SynthSR GPU performance investigation

Investigation date: 2026-09-08. Application code at `fc5aa9a`.

**Implemented fix:** the new `synthsr-blocked-fp32-v1` executor completes the same full FLAIR example in **17.78 seconds**, including **7.25 seconds of inference**, on the same Apple hardware. The released GPU baseline was 140.14 seconds overall and 128.53 seconds of inference. The following section records the implementation validation; the remainder preserves the original investigation.

## Optimized GPU validation

| Implementation | Total processing | Inference, including flip |
| --- | ---: | ---: |
| Released ONNX Runtime WebGPU, repeat | 140.14 s | 128.53 s |
| Released WASM, repeat | 59.99 s | 45.89 s |
| Optimized production build, first | 18.38 s | 7.43 s |
| Optimized production build, repeat | 17.86 s | 7.41 s |
| Final build with model-contract guards | **17.78 s** | **7.25 s** |

The final build is approximately **7.9× faster overall** and **17.7× faster in inference** than the released GPU repeat. Its independent worker-start-to-result wall time was 18.86 seconds; application provenance excludes worker startup. The measurements use the same full-volume FLAIR, flip averaging and sharpening on the same Apple `metal-3` adapter. GPU remains an explicit processing-device choice; the default remains WASM pending wider device measurements.

The optimized path uses a SynthSR-specific executor rather than patching ONNX Runtime internals or replacing shaders through browser hooks. Each convolution workgroup computes a 16-position × 32-channel block using shared FP32 input and weight tiles. Weights are repacked once from the existing checksum-verified ONNX bytes. Intermediate activations stay NDHWC, eligible ELU activations are fused into Conv/Add, and graph-lifetime planning reuses buffers while retaining encoder skips. Full-volume context and the original split-convolution graph are preserved. The generated graph/weight-offset index contains no additional model weights and is reproducible with `scripts/index_gpu_model.py`.

Both earlier production runs produced identical output. Against the known native CPU full-example reference, the final build differed at **424 of 6,598,560 voxels (0.0064%)**, all by exactly one uint8 intensity step; maximum affine difference was 0.00000358 mm. This passes the existing regression thresholds (maximum intensity difference 1, mismatch fraction below 0.1%, affine difference below 0.00002 mm). The prototype was also compared directly against the freshly measured released WASM result: 448 one-step differences and identical affines. A small full-network float32 comparison against WASM had maximum absolute error 0.00000367. These are engineering parity checks, not clinical validation.

Optional timestamp profiling of the full-volume prototype measured approximately 2.79 seconds of GPU work per prediction, of which 2.76 seconds was convolution. The production runs above had profiling disabled. See [raw timings, profiles and numerical comparisons](optimized-gpu-2026-09-08.json), including the final built worker checksum.

Validation completed: 17 unit tests (model pin, buffer lifetimes and skip preservation, graph rejection, dispatch bounds, weight layout and existing spatial/tiling checks); five production browser tests (kernel edge cases against an independent CPU calculation, TensorFlow fixture parity for WASM and GPU, cancellation/download workflow, and cross-origin isolation); five standalone CLI checks. The server browser suite skipped its optional hardware-only full-volume case, which was exercised separately in the shared Apple GPU browser as recorded above. The model index regenerated byte-for-byte. No numerical precision reduction or approximate image tiling was introduced.

## Original finding

**Before the fix, the reported slowdown was reproduced in the released webapp with its built-in FLAIR example.** The second complete run took 140.14 seconds on GPU versus 59.99 seconds on WASM: GPU was 2.34× slower overall and 2.80× slower in inference. Earlier small synthetic-input measurements favored GPU but did not represent this full-volume workload.

## Released webapp: full FLAIR example

Tested https://webapps.neurodesk.org/synthsr/ through its normal UI, sequentially WASM, GPU, WASM, GPU. Loaded Example images → FLAIR once. All four runs used MRI, full-volume mode, flip averaging and sharpening. Input shape was 176×232×159, padded shape 192×256×160, output shape 177×233×160. Hardware was the same Apple `metal-3` adapter and Chrome 150 described below. The released worker URL was `/synthsr/assets/inference-worker-BzExymYu.js`, matching the worker used in the preliminary tests.

| Backend/run | Total processing | Inference (both predictions) | Session initialization | Model loading |
| --- | ---: | ---: | ---: | ---: |
| WASM 1 | 141.98 s | 127.96 s | 4.92 s | 0.26 s |
| GPU 1 | 146.19 s | 134.37 s | 2.53 s | 0.29 s |
| WASM 2 | **59.99 s** | **45.89 s** | 4.14 s | 0.39 s |
| GPU 2 | **140.14 s** | **128.53 s** | 2.91 s | 0.25 s |

These are the original app's provenance timings. Independent worker-start-to-result wall times were 142.24, 146.31, 60.11 and 140.29 seconds. Model bytes were already cached; no downloading advantage explains WASM's faster repeat. Each click still created a fresh worker/session, as in normal application use. We did not alter the deployed inference code or use a synthetic input. A pass-through `Worker` subclass recorded the app's existing result messages and progress timestamps. Raw provenance and stage events are in [released-example-2026-09-08.json](released-example-2026-09-08.json).

The first WASM run's prediction intervals were approximately 94.8 and 33.1 seconds; its repeat's were 26.4 and 19.4 seconds. GPU prediction intervals stayed around 61–68 seconds. These intervals come from progress delivery timestamps and include small orchestration costs. This shows substantial first-use/repeat sensitivity on WASM, consistent with runtime warm-up, but does not by itself prove a specific JIT, cache, thermal or system-load mechanism. These are two runs per backend on one shared device, not a statistically controlled benchmark.

All four runs completed. Repeated outputs were identical within each backend. Comparing the second WASM and GPU results across all 6,598,560 output voxels found 297 differences, each exactly one uint8 intensity step. Output shapes and affines matched. Thus the measured speed difference did not come from a failed or truncated prediction.

For this released-app case, tiled-mode redundancy is **not** the explanation: all four reports have `tiled: false`. The time difference is concentrated in inference. The confirmed naive Conv3D implementation and large full-volume tensors remain the strongest implementation-level explanation for poor GPU throughput. A per-operator profile is still needed to attribute exact shares to convolution, layout conversions, memory traffic and transfers. The earlier small-volume results must not be extrapolated to full brain volumes.

## Preliminary small-input comparison

The existing production preview was tested in the shared T3 browser: Chrome 150, macOS, Apple `metal-3` adapter, `isFallbackAdapter: false`, cross-origin isolation enabled, four WASM threads. The browser does not disclose the exact GPU model. Model SHA-256 matches the application manifest.

| Input | Backend | Session initialization | First inference | Two subsequent inferences |
| --- | --- | ---: | ---: | ---: |
| 32³ | WASM | 6.507 s | 2.297 s | 1.080, 1.353 s |
| 32³ | WebGPU | 2.761 s | 0.265 s | 0.252, 0.209 s |
| 96³ | WASM | 3.396 s | 37.201 s | 36.711, 27.510 s |
| 96³ | WebGPU | 4.235 s | 5.934 s | 5.895, 5.906 s |

Warm means are 1.216 versus 0.230 seconds for 32³, and 32.110 versus 5.900 seconds for 96³. This is approximately 5.3–5.4× faster on GPU in this small sample, with substantial WASM timing variability. It is not a controlled cross-device benchmark or a full-volume comparison.

Method: fetched the deployed production worker `inference-worker-BzExymYu.js` into an isolated diagnostic Blob worker, retaining its runtime and session factory. Replaced only its message handler to call the session directly. Each backend used a fresh worker/session and the same model and deterministic float32 tensor (`input[i] = (i % 997) / 997`, shape `[1,1,...dims]`). Ran three sequential predictions on each session, with CPU output and disposal between calls. The benchmark excluded downloading, NIfTI preparation, flip augmentation, tiling and postprocessing. Timings include CPU orchestration and transfers within `session.run`; the near-zero later `getData()` time does **not** establish negligible GPU download cost. Three sampled outputs agreed within about 1.5e-7; this spot check is not a full parity test. No per-operator GPU timing profile was collected.

See [raw measurements](performance-2026-09-08.json). The additional shader-capture run is excluded from those timing comparisons. Diagnostic workers were terminated after completion; production code and deployment were not modified.

## Confirmed GPU implementation limitation

SynthSR's exported graph contains 23 convolutions, of which 22 have 3×3×3 kernels. ONNX Runtime 1.29's rank-5 branch explicitly uses `Conv3DNaiveProgram` and returns before the optimized 2D matrix-multiplication paths. Its CPU convolution implementation routes kernel ranks 1–3 through MLAS. Sources: [WebGPU Conv dispatch](https://raw.githubusercontent.com/microsoft/onnxruntime/v1.29.0/onnxruntime/core/providers/webgpu/nn/conv.cc), [CPU Conv dispatch](https://raw.githubusercontent.com/microsoft/onnxruntime/v1.29.0/onnxruntime/core/providers/cpu/nn/conv.cc).

A separate browser run intercepted shader-module creation without changing the descriptors. It confirmed that the deployed runtime actually creates `Conv3DNaive` shaders: one output element per invocation, nested loops over kernel positions and input channels, float32 storage, 64-invocation workgroups, and no shared-workgroup tile or subgroup arithmetic in the convolution body. The generated header enables subgroups, but the convolution does not use the subgroup parameters. The captured convolution uses channels-last activations after runtime layout transformation; it would be incorrect to blame this run solely on the exported NCDHW layout. Transpose, ELU and BatchNormalization shader modules were also observed. Module creation counts are not dispatch counts.

This is strong implementation evidence for limited GPU efficiency, not a measurement attributing a particular percentage of total time to convolution. Simply enabling WebGPU does not supply a CUDA/cuDNN-style optimized 3D convolution implementation.

The example's padded 192×256×160 graph requires about 1.217 trillion convolution multiply-accumulates per prediction, calculated from inferred output and weight shapes (including padded kernel positions). Its 48-channel float32 tensor occupies 1.406 GiB; multiple live tensors and intermediate passes add memory traffic. The existing decoder concat split avoids a larger allocation, but adds intermediate outputs and additions. Both backends use this same rewritten model.

## Confirmed tiled-mode waste

[`runTiled`](../../../packages/synthsr/src/tiling.js) evaluates 96³ patches at a 32-voxel output stride. For the example shape 192×256×160:

- 6×8×5 = 240 model calls per prediction.
- 240×96³ / (192×256×160) = **27 times** the processed voxel count of one full-volume pass. The convolution work scales accordingly, apart from boundary effects and different kernel efficiency.
- Boundary clamping gives only **72 distinct patches**: 168 calls repeat input patches already evaluated during that prediction.
- Default flip augmentation runs both predictions, bringing the total to **480 calls**.

These counts were verified by executing the actual shared tiler with a deterministic coordinate-coded volume and a mock network that records patch origins. Existing tile extraction/assembly tests also passed when their import was redirected to the shared source: this worktree has no installed workspace dependencies, so their normal package import could not resolve.

At the measured 5.9 seconds per 96³ GPU prediction, 480 calls would imply roughly **47 minutes of inference**. This is an extrapolation, not a measured full tiled run. It explains how selecting tiled GPU processing can be dramatically slower than full-volume CPU processing, even when GPU wins for identical work. Tiling is a memory workaround, not a speed option. This penalty affects WASM too when it uses the same tiled settings.

Repeated patches can be evaluated once and scattered into all their assigned output cores without changing the current tiling context. For this example that would reduce calls from 240 to 72 per prediction. This is a concrete optimization opportunity, not an implemented or measured speedup. Increasing the core or reducing the halo would instead change prediction context and requires separate validation.

## Other costs and limits of the diagnosis

The [application](../src/main.js) creates a worker for each run and terminates it on completion. The [pipeline](../../../packages/synthsr/src/pipeline.js) recreates/releases the session and, by default, predicts the original and flipped image. Cached model bytes do not preserve a live session. Startup is material for tiny inputs; it does not explain the persistent 96³ GPU inference time. The elapsed UI time includes stages beyond inference, while downloaded provenance separates `model`, `initialize`, `inference`, and other stages.

The [GPU session configuration](../src/inference-worker.js) explicitly disables CPU execution-provider fallback. Successful runs therefore do not silently move unsupported network operators to WASM. CPU preprocessing and orchestration still exist. The measured adapter is hardware, although the ordinary Playwright test configuration deliberately uses SwiftShader unless `SYNTHSR_HARDWARE_GPU` is set; those default CI results must not be used as hardware GPU benchmarks.

The older 98/151-second full-volume GPU validation records contained no paired browser-WASM measurements. The released-app runs above now provide that comparison. The standalone package uses native CPU ONNX Runtime and is a different backend from browser WASM; its timings should not be substituted for browser WASM timings.

The released-example comparison established the slowdown on this device and motivated the optimized executor validated above. Deduplicating boundary patches remains a separate application-level opportunity for tiled mode. Session reuse can reduce startup costs, but the original roughly 83-second inference gap on the repeat was much larger than session initialization. FP16 was not needed for the measured improvement.
